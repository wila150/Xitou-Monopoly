# LINE 闖關系統｜國介＆禾康溪頭大富翁

依據 `LINE闖關系統_架構設計文件(2).docx`（v2 版）為基礎、再依實際討論調整過的 LINE 官方帳號後端。全程以 LINE 文字指令驅動，小編不需要另外的網站後台。

## 遊戲機制

- **12 關分兩種過關方式**：
  - 6 關有現場關主（B3、B4、D6、A3、A5、C4）——關主評估完成後口頭給關鍵字（目前每關 10 組共用同一個關鍵字，就是關卡代號本身，例如 B3 關的關鍵字就是「B3」），隊伍打進 LINE 立即解鎖下一關。
  - 6 關沒有關主（A2、D5、C5、B6 拍照，E2、E3 錄影）——隊伍直接在 LINE 對話上傳照片／影片，**系統不會自動過關**，只會回覆「請等待小編確認」並推播通知小編；小編到官方帳號聊天記錄看過內容沒問題後，輸入「通過 X組」才真正解鎖下一關。
  - `通過 X組` 這個指令**不限關卡類型**，小編對關主的關卡也可以用它當手動捷徑（例如隊伍回報「已完成 B3」，小編確認後直接喊過，不一定要隊伍自己打關鍵字）。
- **不再有「完賽」自由回報**：計時只能靠隊伍實際人在 B6、由 **B6 終點工作人員**觸發「到站 X組」才會停止。這是刻意設計成「現場才能觸發」，避免隊伍還沒到站就自稱完賽。
- **12:30 只凍結進度，不會幫忘記回報的隊伍自動產生成績**：時間一到，系統停止受理新的關卡進度（`完成關卡數`不再增加），但仍持續等待每一組實際到站辦理終點確認，逾時到站一樣會有成績，只是標註「逾時」。
- **10 組各有專屬路線順序**（見下方「路線表」），第 10 組比較特別：第 1 關就是 B6，最後一關（B3）破完後直接回 B6 辦終點確認，不需要重做一次 B6 的任務。

## 系統架構

- **Express**：接收 LINE Webhook、提供關卡地圖圖片的靜態網址
- **@line/bot-sdk v11**：Webhook 簽章驗證、回覆／推播訊息；同時處理文字訊息與圖片／影片訊息
- **PostgreSQL**（`pg` 套件）：資料庫是獨立的 Postgres 服務，不會因為網頁服務重開機／被雲端平台自動關機而遺失資料（詳見下方「部署」的說明）
- **node-cron**：12:15 提醒、12:30 停止受理新關卡進度兩支排程

```
src/
  index.js              Express 入口、Webhook 路由（文字走 commandRouter，圖片／影片走 teamService.verifyMedia）
  db.js                 Postgres 連線池、schema、交易 helper
  lineClient.js         LINE SDK 包裝（reply / push）
  scheduler.js          12:15 提醒／12:30 停止受理新關卡進度排程
  config/
    event.js            時間控管參數（12:15 / 12:30）
    admins.js            小編（管理員）userId 名單
    checkpoints.json     12 關的名稱／任務說明／地圖檔名／過關方式（活動前請填寫，見下方 CSV 工作流程）
    checkpoints.js        讀取並驗證上面這份 JSON
    teamsRoute.json      10 組官方路線順序＋6 個關主關卡的專屬關鍵字（活動前請填寫，見下方 CSV 工作流程）
    teamsRoute.js         讀取並驗證上面這份 JSON
  services/
    teamService.js        核心商業邏輯（報到／出發／過關／終點確認／排名…）
    timeUtil.js            時間格式化與 12:30 判斷
  handlers/
    commandRouter.js       文字指令解析與分派
scripts/                  CSV 匯出／匯入工具（見下方）
public/maps/              9 張定點關卡地圖圖片放這裡
```

## 活動前必做的事（不需要寫程式，用 Excel／Google Sheets 就能填）

系統資料實際存在 JSON 裡，但不需要直接手改 JSON——用以下指令匯出成 CSV，編輯後再匯回，匯入時會自動檢查資料完整性（缺關卡、關鍵字重複等），檢查不過不會覆寫檔案：

- ✅ **10 組官方路線順序**：已依文件「四、10組正式路線表」寫入 `src/config/teamsRoute.json`（第 10 組的特例——第 1 關是 B6——也已處理好，程式邏輯本身不需要特別分支，因為終點確認一律是獨立動作）。
- ✅ **關卡任務內容、位置、地圖圖片、過關方式**：已依「國介＆禾康 闖關活動細節表」（含 0914 版的補充，例如 E3「請自備礦泉水」）、v2 文件的關主配置、與溪頭步道導覽圖填入 `src/config/checkpoints.json` 與 `public/maps/`。B4「百步穿揚」的位置（星光教室）已確認無誤。
- ✅ **6 個有關主關卡的關鍵字**：目前設計是**每一關 10 組共用同一個關鍵字，就是關卡代號本身**（例如 B3 關的關鍵字就是「B3」、B4 關就是「B4」），不是每組各給不同密語。這樣關主現場只需要記自己那一關的一個字，不需要對照 10 組不同密語的清單。

  ⚠️ 這個設計的取捨：因為關鍵字不再是每組專屬，如果隊伍看到其他組輸入密語、或知道密語是關卡代號本身，理論上可以跳過任務直接輸入過關。防作弊主要依賴「關主確認完成後才告知」這一層，密語本身不再是秘密。如果活動方之後想改回每組不同的密語，用下面的 CSV 流程即可覆蓋，系統會檢查同一關卡的關鍵字在 10 組之間是否一致（目前）或允許各自不同（如果改回 60 組互不相同的設計）。

```bash
npm run routes:export        # 匯出 -> data/teams-route.csv
#   用 Excel/Sheets 開啟，verifyType 欄位是唯讀參考——只有 'keyword' 的列才要填 keyword，
#   'photo' / 'video' 的列請保持 keyword 欄位空白。存檔後：
npm run routes:import        # 檢查並寫回 -> src/config/teamsRoute.json
```

> 關鍵字請避開系統保留字：「報到」「出發」「到站」「通過」「完賽」「進度」「排行榜」「目前關卡」「闖關進度」「遊戲結束」「重置遊戲」「接任隊長」「確認換隊長」「解除綁定」，以及所有「數字+組」的格式（例如「5組」），系統會先比對這些指令，比對不到才視為關鍵字嘗試。

若關卡內容、位置或過關方式之後有異動，一樣可以用 `npm run checkpoints:export` / `checkpoints:import` 編輯 `checkpoints.json`（CSV 工作流程用法同上）。

## 環境設定

> 需要 **Node.js 22 以上**（`@line/bot-sdk` v11 的硬性需求）。可用 `node -v` 確認，不夠新的話用 [nvm](https://github.com/nvm-sh/nvm) 或官網安裝新版。

### 本機開發

1. 安裝並啟動本機 PostgreSQL（Mac 用 Homebrew）：
   ```bash
   brew install postgresql@16
   brew services start postgresql@16
   createdb line_checkpoint_dev
   ```
2. 複製 `.env.example` 為 `.env`，填入：
   - `DATABASE_URL=postgres://<你的系統帳號>@localhost/line_checkpoint_dev`，`PGSSL=false`
   - `LINE_CHANNEL_ACCESS_TOKEN`、`LINE_CHANNEL_SECRET`（見下方 LINE 設定）
   - `ADMIN_USER_IDS`：小編（可用管理指令的人）的 LINE userId，多人用逗號分隔
   - `PUBLIC_BASE_URL`：伺服器對外網址（LINE 平台會來抓地圖圖片，必須是 https）
3. 安裝套件並啟動：
   ```bash
   npm install
   npm start
   ```
   第一次啟動會自動建立資料表（見 `src/db.js` 的 `init()`）。
4. 本機測試可用 `ngrok http 3000`（或 cloudflared）取得暫時 https 網址，設定回 `.env` 的 `PUBLIC_BASE_URL`，並到 LINE Developers Console 的 Webhook URL 填 `https://your-ngrok-domain/webhook`，開啟「Use webhook」。
5. LINE 官方帳號後台記得把「自動回覆訊息」關閉，否則圖片／影片訊息可能會先被官方帳號內建的自動回覆擋掉。

### LINE 官方帳號設定 Messaging API

如果你的 LINE 官方帳號原本只有在用「LINE Official Account」介面（發群發訊息、圖文選單那種），Messaging API 是另一個要另外啟用的頁籤，兩者可以掛在同一個官方帳號上：

1. 到 [LINE Developers Console](https://developers.line.biz/console/)，用同一組 LINE 帳號登入
2. 建立一個 Provider，底下建立 **Messaging API Channel**（會掛到你現有的官方帳號，不會變成兩個帳號）
3. 進去該 Channel 的「Messaging API」頁籤：取得 **Channel access token**、**Channel secret**，設定 **Webhook URL** 為 `https://你的網址/webhook` 並開啟「Use webhook」
4. 建議把「自動回應訊息」「加入好友歡迎訊息」都關閉，避免跟 bot 邏輯衝突

### 部署到 Render（免費方案可行，但有一個重要前提）

Render 免費的網頁服務（Web Service）檔案系統是暫時性的：只要閒置 15 分鐘被自動關機、下次請求進來喚醒，本機檔案就會被清空。**這就是這個系統改用 Postgres、而不是本機 SQLite 檔案的原因**——資料庫是獨立服務，網頁服務重開機不會動到它。做法：

1. Render 建立一個 **PostgreSQL** 服務（免費方案即可，一個資料庫 30 天效期，活動前一兩天建立即可涵蓋整個活動）
2. 複製它的 **Internal Database URL**，貼到 Render 網頁服務的環境變數 `DATABASE_URL`（Render 內部連線預設會用 SSL，`.env.example` 裡的 `PGSSL` 可以不用設）
3. 建立 Render **Web Service**，指到這個專案的 repo，Build Command 用 `npm install`、Start Command 用 `npm start`
4. 把 `.env` 裡其他變數（`LINE_CHANNEL_ACCESS_TOKEN`、`LINE_CHANNEL_SECRET`、`ADMIN_USER_IDS`、`PUBLIC_BASE_URL` 設成 Render 給的網址）也加進 Render 的環境變數
5. 免費方案仍然會閒置關機、下個請求要等約 1 分鐘喚醒——活動當天報到開始前，記得先手動 `curl` 一次 `/health` 把服務叫醒，並且活動全程盡量保持有人陸續在傳訊息（自然就會一直保持喚醒狀態）

### 如何取得某人的 LINE userId（設定 ADMIN_USER_IDS 用）

讓要設定為小編的帳號傳一句話給官方帳號，伺服器 log 目前不會印出 userId；若需要，可暫時在 `src/index.js` 的 `handleEvent` 開頭加一行 `console.log(userId)` 除錯，取得後記得移除。

### 關於「到站 X組」的設計選擇

v2 文件把「B6 終點怎麼停止計時」列為待確認事項，列出三個方案（固定密碼／系統動態產生一次性代碼／QR Code），文件建議用「現場工作人員一次性代碼，隊長輸入」。討論後我們選了**功能等價、但更簡單可靠的做法**：不是隊長輸入代碼，而是**B6 工作人員直接輸入「到站 X組」**——跟現有「出發 X組」完全相同的模式（現場角色觸發、不需要另外的權限分級）。安全性一樣是「只有人在現場才能觸發」，但少了「代碼產生→念給隊長→隊長輸入」這三個步驟，也不需要另外維護代碼的產生與過期邏輯。如果之後想改成隊長輸入代碼的版本，改動範圍在 `teamService.finishAtB6` 與 `commandRouter.js` 的 `到站` 分支。

## 與文件的實作對應說明

- 文件狀態①已報到／②待出發在系統裡合併為單一狀態 `CHECKED_IN`：文件中這兩個階段之間沒有獨立觸發指令，行為描述相同（尚未計時、不公布關卡地點）。
- 排名規則只定義了「已終點確認」隊伍之間的排序。本系統把所有隊伍分兩桶：準時終點確認（12:30 前）排最前面，其餘（逾時終點確認、闖關中、尚未出發）都算後段，桶內再依完成關卡數、總耗時排序；尚未有總耗時的隊伍並列在同關卡數的最後。
- B4「星光教室」的位置：文件與溪頭步道導覽圖原本都標註為「推測」，已向活動方確認無誤，`public/maps/B4.jpg` 目前的裁切位置不需要再調整。
- 「到站 X組」的設計選擇見上一節說明。

## 已知風險與對應的保護措施

實作過程中發現並修掉的幾個邊界情況，記錄下來方便之後維護：

- **「通過」現在會檢查是否已凍結進度**：一開始只有關鍵字比對會擋 12:30／遊戲結束後的新進度，「通過」被漏掉了，導致小編理論上可以在凍結後繼續把任何一組從頭推到尾。已修正為兩者行為一致。
- **報到會驗證組別編號**：`報到 99組` 這種不存在的組別以前會被接受，之後只要碰到「出發」之類需要讀路線表的指令就會拋例外、使用者完全沒有任何回覆。現在報到時就會直接拒絕不合法的組別編號。
- **任何未預期的伺服器錯誤，使用者都會收到保底回覆**（「系統發生錯誤，請稍後再試」），而不是完全沒有回應——這樣使用者才知道是系統出狀況，而不是以為訊息沒送出去。
- **`通過`／`到站` 都沒有辦法事前防止手滑重複觸發**（`通過` 不像 `出發`／`到站` 天然冪等，連按兩次會多跳一關）；沒有做成事前攔截是因為早期版本試過用時間或關卡索引去猜測「這是不是重複」，但小編合理的快速連續操作（一次確認好幾組不同的送審）反而會被誤判擋掉。改用**事後可以更正**的方式：`退回 X組` 可以把誤觸的通過／到站復原，比起自動偵測「是不是手滑」更可靠。

## 自動化測試

`tests/commandRouter.test.js` 用 Node 內建的 `node:test` 涵蓋了報到（含無效組別）、出發、關鍵字解謎、照片／影片送審與小編通過、關卡型態不符提示、凍結後拒絕通過、退回更正、到站終點確認、管理指令權限、遊戲結束凍結、換隊長、解除綁定、排行榜開關、重置遊戲等核心流程。測試需要連到一個 Postgres（預設接本機的 `line_checkpoint_test`，每個測試開頭都會先重置遊戲、彼此不會互相汙染）：

```bash
createdb line_checkpoint_test   # 只需要建立一次
npm test
```

也可以用 `TEST_DATABASE_URL` 指到其他 Postgres（例如另一台機器）：
```bash
TEST_DATABASE_URL=postgres://user:pass@host/db npm test
```

修改 `src/services/teamService.js` 或 `src/handlers/commandRouter.js` 後，建議先跑一次確認沒有破壞既有行為。

## 測試建議

活動前務必找 10 支測試帳號（或用 `重置遊戲` 指令重複重置後用同幾支帳號分批測試）跑過完整流程：報到 → 出發 → 依序完成 12 關（含關主關卡的正確／錯誤關鍵字測試、無關主關卡上傳照片／影片後小編輸入「通過 X組」）→ 到站辦理終點確認；並測試 `遊戲結束`、`接任隊長`／`確認換隊長`、`解除綁定`、12:15 提醒與 12:30 停止受理新關卡進度（可暫時把 `src/config/event.js` 的時間改成接近目前時間來測試排程是否正確觸發，測完記得改回來）。也務必實測第 10 組的特例路線（第 1 關 B6 → … → 第 12 關 B3 → 回 B6 到站），確認不會被要求重做一次 B6 任務。務必提醒實際負責審核照片／影片的小編：看到推播通知後要記得回「通過 X組」，否則隊伍會卡在原地等確認。
